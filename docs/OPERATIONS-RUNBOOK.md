# 글리프 웹 운영 런북

## 매일 확인

- 결제·광고 웹훅 실패율, 중복 이벤트, 쿠키 원장 불일치를 확인합니다.
- 긴급 신고(구체적 위해, 개인정보 노출, 성착취물)는 즉시 숨김 후 검토합니다.
- 작가 원고와 관리자 페이지 접근 로그에서 비정상 조회를 확인합니다.
- 백업 성공 여부와 장애 알림 채널을 확인합니다.

## 작가 등록 심사

1. 담당자는 MFA가 적용된 개인 관리자 계정으로 접속합니다.
2. 포트폴리오 또는 비공개 원고를 확인하고 저작권·표절 위험, 정책 적합성, 연재 가능성을 기록합니다.
3. 승인 또는 보완 요청 사유를 남깁니다. 승인 처리는 `review_author_application()` RPC를 통해 감사로그와 함께 기록합니다.
4. 심사 원고는 이의제기 기간 종료 후 삭제하고 삭제 기록을 남깁니다.

## 신고 처리

1. `received` 신고를 위험도에 따라 분류합니다.
2. 원문, 작성자, 시각, 관련 신고를 보존하고 필요한 경우 임시 숨김합니다.
3. 삭제·경고·계정 제한 또는 문제없음 결정을 내리고 근거를 기록합니다.
4. 일반 신고는 72시간 이내 1차 확인을 목표로 합니다. 제재 대상자는 14일 이내 이의를 제기할 수 있습니다.
5. 저작권 신고는 권리자 확인, 대상 특정, 소명과 복원 절차를 별도로 진행합니다.

## 결제·광고 사고

- 프런트엔드에서 잔액을 수동 조정하지 않습니다.
- 공급자 대시보드의 이벤트 ID와 `cookie_ledger.idempotency_key`를 대조합니다.
- 웹훅 비밀 유출이 의심되면 즉시 비밀을 교체하고 해당 기간의 모든 이벤트를 재검증합니다.
- 환불은 원거래와 연결된 별도 원장 항목으로 남기며 잔액 부족 시 정책에 따라 잠금 또는 미수 처리합니다.

## 개인정보 사고

1. 노출 경로를 차단하고 비밀키·세션을 폐기합니다.
2. 영향 데이터, 사용자, 기간, 접근자를 감사로그로 특정합니다.
3. 관계 법령의 신고·통지 요건을 개인정보보호 책임자와 확인합니다.
4. 사용자 통지에는 발생 내용, 영향, 대응, 이용자 조치, 문의처를 포함합니다.

## 배포와 되돌리기

- `main` 보호 브랜치에 PR 리뷰와 테스트 통과를 필수로 설정합니다.
- GitHub Pages 배포 전 스테이징 Supabase에서 마이그레이션과 RLS 테스트를 통과시킵니다.
- DB 마이그레이션은 앞으로만 적용하며, 되돌릴 때는 데이터 보존용 보상 마이그레이션을 사용합니다.
- 장애 시 직전 정상 커밋을 다시 배포하고 결제·광고 웹훅은 필요하면 공급자 측에서 일시 중단합니다.
